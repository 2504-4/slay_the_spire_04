# JavaFX 杀戮尖塔项目完整说明

**项目定位：** 基于 Java 和 JavaFX 的单机回合制卡牌战斗原型  
**说明日期：** 2026 年 9 月 15 日  
**适用场景：** 项目介绍、课程展示、答辩准备、开发交接和技术交流

本项目围绕“抽取卡牌、分配能量、进行攻防、选择奖励、挑战下一关”构建了一套可交互的桌面游戏流程。它的价值不仅是展示卡牌和按钮，更在于把战斗规则、流程控制和界面反馈组织成一个可理解、可扩展的程序。当前实现包含四个连续关卡、七种卡牌以及三次战后选牌机会，适合用来说明 Java 面向对象设计、JavaFX 事件处理和状态驱动的业务流程。

全文先从玩家视角说明项目，再介绍代码结构和关键设计，最后说明测试、运行方式与改进方向。正文中的“当前实现”指现有代码；设计文档提出但代码尚未具备的接口、快照等内容，放在版本差异和后续设计中单独介绍。

## 1 项目概述与目标

### 1.1 项目是什么

这是一个以《杀戮尖塔》的卡牌战斗形式为参考的 JavaFX 桌面项目。玩家不是实时移动角色，而是在自己的回合内观察手牌、能量和敌人意图，选择攻击或防御；结束回合后，由敌人执行行动，随后进入下一轮。

玩家需要连续击败三个小怪和一个最终 Boss。前面三个敌人被击败后，系统提供三张随机奖励卡，玩家选择一张加入自己的牌组，再进入下一关。生命值不会因进入新关卡而自动恢复，因此当前回合的防御选择会影响后续关卡的生存能力。

准确的项目名称可以表述为：**基于 JavaFX 的杀戮尖塔简化版卡牌战斗系统**。它是玩法和软件结构的教学原型，不是对原作所有系统的完整复刻。

### 1.2 项目希望展示什么

项目主要展示四方面能力：

- **规则建模。** 将生命值、格挡、能量、卡牌和牌堆转换为对象、属性与方法。
- **流程组织。** 将玩家行动、敌人行动、奖励选择和通关判定连接成完整路径。
- **界面交互。** 使用 JavaFX 展示状态、接收点击并反馈操作结果。
- **工程设计与验证。** 用职责划分降低修改影响，通过测试检查规则和状态变化。

项目的策略性主要来自资源约束和信息判断，而不是卡牌数量本身。玩家需要在有限能量下决定如何兼顾伤害输出与生命保留，并通过奖励逐步改变牌组。

### 1.3 一句话说明

> 这是一个用 JavaFX 实现的单机回合制卡牌游戏：玩家通过有限能量打出攻击和防御卡，连续挑战四个敌人，并利用战后奖励逐步强化牌组。

| 功能 | 玩家可见表现 | 对应实现 |

### 2.2 当前不包含的系统

当前主运行路径中没有地图分支、商店、遗物、药水、随机事件、角色选择、存档读档、联机对战、排行榜或数据库服务，也没有实现完整的音效和战斗动画系统。

界面显示了牌堆的**数量**，但没有实现设计文档中通过 `showPile()` 查看整叠卡牌内容的端口功能。不能把文档中的接口草稿直接描述为已完成的界面能力。

## 3 完整游戏流程

### 3.1 从开始到结束的主流程

```text
启动程序
  → 显示主菜单
  → 点击开始游戏
  → 创建控制器 玩家 初始牌组和第一关敌人
  → 洗牌并抽取第一回合手牌
  → 玩家查看敌人意图并出牌
  → 结束回合并结算敌方行动
  → 若双方仍满足继续战斗条件 则进入新回合
  → 击败前三关敌人后选择奖励并进入下一关
  → 击败最终 Boss 后整局胜利
  → 任意敌方行动导致玩家生命归零 则整局失败
```

### 3.2 新一局的初始状态

| 项目 | 当前值 |
| --- | --- |
| 玩家最大生命与初始生命 | 80 |
| 每回合能量上限 | 3 |
| 回合开始时尝试抽牌数 | 5 |
| 手牌上限 | 10 |
| 初始牌组 | 5 张打击与 5 张防御，共 10 张 |
| 初始关卡 | 第 1 关 |
| 第一个敌人 | 史莱姆，25 生命，4 基础攻击 |
| 首次敌方意图 | 固定为攻击 |
| 初始玩家格挡与敌人格挡 | 均为 0 |

“每回合抽 5 张”更精确的含义是尝试抽取最多 5 张。如果达到手牌上限，或抽牌堆与弃牌堆都没有卡，抽牌会提前停止。

### 3.3 玩家每回合需要做的决策

玩家首先读取敌人即将执行的意图，再决定如何分配能量。攻击牌可以缩短战斗，但可能让玩家承受伤害；防御牌可以保留生命，却会占用本回合可用于攻击的能量。

回合结束时未使用的手牌会全部进入弃牌堆，剩余能量也不会累积到下一回合。下一回合能量直接恢复为 3，而不是在剩余能量上再加 3。因此，玩家通常需要结合当前手牌尽量合理使用本回合资源。

### 3.4 战斗中的两个不同终点

- **击败当前小怪：** 只代表当前遭遇结束，进入奖励选择，不代表整局胜利。
- **击败第四关 Boss：** 才代表整局通关。

这一差别决定了状态控制和测试方式。不能只检测敌人死亡，就把游戏判定为通关。

## 5 架构分层与职责

### 5.1 总体结构

项目采用 MVC 思路，将展示、协调和规则分开：

```text
用户点击
  → View 接收操作
  → Controller 校验流程并组织动作
  → Model 执行规则并更新数据
  → View.update 重新读取状态并刷新显示
```

这是职责上的分层，而不是已经严格实现依赖倒置的接口架构。当前视图会读取控制器返回的模型对象，也直接使用 `GameModel` 中的类型，因此仍然存在视图对模型的类型依赖。

### 5.2 View 负责什么

`MenuView` 负责主菜单，通过 `Runnable` 回调告诉入口类“开始游戏被点击”，不负责创建玩家或判断胜负。

`GameView` 负责战斗画面，包括生命条、格挡、意图、能量、卡牌按钮、日志以及结束回合和重新开始按钮。它把操作转发给控制器，在操作之后调用 `update()` 刷新画面。

视图不负责计算攻击造成多少生命损失，也不负责决定奖励池内容。这样修改颜色、布局或按钮样式时，通常不需要修改战斗规则。

### 5.3 Controller 负责什么

`GameController` 负责整局流程，包括：

- 创建并持有模型、玩家和当前敌人。
- 检查当前是否允许出牌、结束回合或选择奖励。
- 组织玩家回合与敌方回合的先后顺序。
- 判断小怪战胜、最终胜利与玩家失败。
- 生成奖励候选，推进关卡。
- 维护战斗日志与查询方法。

控制器并非完全“薄”的转发层。关卡、奖励、胜负和日志都在这里，因此它既是协调者，也承担了较多流程业务。

### 5.4 Model 负责什么

`GameModel` 内部定义了卡牌、玩家和敌人的规则。卡牌决定牌效，玩家管理生命、格挡、能量和牌堆，敌人管理生命、格挡和行为意图。

模型和控制器的代码不依赖 JavaFX 控件，可以在不创建游戏窗口的情况下运行规则与控制流程测试。这是现有分层最直接的测试价值。

### 5.5 当前分层的边界

控制器通过 `getPlayer()`、`getEnemy()` 等方法返回对象，玩家的牌堆 getter 又直接返回可变列表。因此“界面通常不主动修改模型”与“界面不可能修改模型”是两回事。当前实现属于前者，还没有形成严格只读的状态访问边界。

## 6 核心类与对象关系

### 6.1 Main

`Main` 继承 JavaFX 的 `Application`。它创建主窗口，首先展示菜单，再通过回调切换到战斗场景。

窗口初始尺寸为 900 × 820，并设置对应的最小宽高。进入游戏时创建新的 `GameController` 和 `GameView`。入口类同时注册默认未捕获异常处理器，用于把异常输出到标准错误流；这属于错误记录，不等于自动恢复游戏状态。

### 6.2 GameController

重要状态如下：

| 字段 | 含义 |
| --- | --- |
| `model` | 模型外部对象，用于创建内部对象 |
| `player` | 本局玩家，跨关卡保留 |
| `enemy` | 当前敌人，进入下一关时替换 |
| `currentLevelIndex` | 从 0 开始的关卡下标 |
| `gameOver` | 整局是否结束 |
| `playerWin` | 结束原因是否为玩家通关 |
| `playerTurn` | 是否处于允许玩家回合操作的阶段 |
| `rewardPending` | 是否正在等待奖励选择 |
| `rewardChoices` | 当前奖励候选 |
| `battleLog` | 最多保留 100 条的战斗日志 |

界面展示的关卡号由下标加 1 得到。`isPlayerLose()` 使用 `gameOver && !playerWin` 判断失败。

控制器的 `startGame()` 是私有方法，由构造函数调用。当前重新开始不是外部再次调用该方法，而是创建新控制器。

### 6.3 Card 及具体卡牌

`Card` 是抽象类，定义名称、描述、费用、类型和抽象方法 `play(Player player, Enemy enemy)`。七种卡牌分别继承它并实现自己的效果。

当前 `Card`、具体卡牌、`Player` 和 `Enemy` 都是 `GameModel` 的非静态内部类，例如通过 `model.new Player()` 创建玩家。它们不是已经拆分为独立源文件的顶层实体。

### 6.4 Player

玩家负责自己的资源和牌堆。主要方法包括：

| 方法 | 主要作用 |
| --- | --- |
| `startTurn()` | 恢复能量、清玩家格挡、尝试抽 5 张 |
| `drawCard()` | 处理手牌上限、空堆与弃牌回收 |
| `playCard(card, enemy)` | 检查卡牌和费用，扣费并结算 |
| `endTurn()` | 把剩余手牌移入弃牌堆 |
| `prepareForNewEncounter()` | 新关前合并流转牌堆并洗牌 |
| `addCard(card)` | 把新卡加入牌组记录和弃牌堆 |
| `takeDamage(damage)` | 格挡优先抵伤，生命不低于 0 |
| `gainBlock(amount)` | 增加格挡 |

### 6.5 Enemy

敌人没有能量和手牌系统。它通过当前意图直接执行攻击、防御或攻防组合。

`startTurn()` 清除敌人旧格挡，`act(player)` 执行当前意图，`endTurn()` 生成下次意图。不同关卡复用同一种敌人类，差异来自名称、生命和基础攻击配置，而不是四套不同的行为算法。

### 6.6 没有实现的继承关系

尽管概要设计部分文字提到 `Person` 或 `Combatant`，当前 `Player` 和 `Enemy` 并未继承一个统一的战斗单位基类。二者各自维护生命与格挡，并各自实现受伤逻辑。对外说明时应避免画出代码中不存在的继承关系。

## 7 卡牌系统与能量机制

### 7.1 当前卡牌配置

| 卡牌名称 | 具体类 | 费用 | 类型 | 效果 | 获取方式 |
| --- | --- | --- | --- | --- | --- |
| 打击 | `StrikeCard` | 1 | 攻击 | 造成 6 点伤害 | 初始牌组 |
| 防御 | `DefendCard` | 1 | 技能 | 获得 5 点格挡 | 初始牌组 |
| 铁斩波 | `IronSlashCard` | 1 | 攻击 | 造成 7 点伤害并获得 7 点格挡 | 战后奖励 |
| 重锤 | `HeavyHammerCard` | 2 | 攻击 | 造成 24 点伤害 | 战后奖励 |
| 城墙 | `WallCard` | 2 | 技能 | 获得 20 点格挡 | 战后奖励 |
| 究极打击 | `UltimateStrikeCard` | 1 | 攻击 | 造成 10 点伤害 | 战后奖励 |
| 究极防御 | `UltimateDefendCard` | 1 | 技能 | 获得 8 点格挡 | 战后奖励 |

卡牌类型主要用于分类和界面样式，不是效果的唯一依据。例如铁斩波属于攻击牌，却同时提供格挡；真正的效果由它重写的 `play()` 决定。

### 7.2 为什么使用多态

玩家出牌逻辑只需调用 `card.play(this, enemy)`，不必通过卡名逐一判断牌效。增加一种新卡时，可以继承 `Card` 实现效果，而不改动通用扣费和移牌逻辑。

不过这不代表新增卡牌完全不改现有代码。如果希望新卡进入奖励池，还必须修改 `createRewardChoices()`；如果增加新的卡牌类别，也需要检查分类和界面样式。

### 7.3 费用与使用限制

当前费用为 1 或 2，玩家每回合能量为 3。因此，在仅使用 1 费卡且手牌允许时，最多可以打出三张；使用一张 2 费卡后，通常还剩 1 点能量可使用一张 1 费卡。

出牌模型同时检查：卡不为空、卡确实在手牌中、能量足够。控制器还检查手牌下标和流程状态。选择奖励卡则不扣能量，奖励卡上的费用是它之后在战斗中使用时的费用。

### 7.4 一个具体回合示例

假设第一回合抽到了两张打击和三张防御。玩家初始生命为 80、能量为 3，敌人生命为 25，当前意图为攻击 4。

| 操作 | 剩余能量 | 敌人生命 | 玩家格挡 | 玩家生命 |
| --- | --- | --- | --- | --- |
| 初始状态 | 3 | 25 | 0 | 80 |
| 打出一张打击 | 2 | 19 | 0 | 80 |
| 打出一张防御 | 1 | 19 | 5 | 80 |
| 再打一张打击 | 0 | 13 | 5 | 80 |
| 结束回合后敌人攻击 | 0 | 13 | 1 | 80 |
| 新玩家回合准备完成 | 3 | 13 | 0 | 80 |

最后两行是同一次结束回合操作中的内部阶段。界面通常在流程完成后刷新，显示的是新回合的状态，而不是把每一个中间阶段分别播放出来。

这个例子体现了格挡的作用时机：先用格挡承受当前敌人的攻击，再在新玩家回合开始时清除剩余格挡。

## 8 牌堆循环与状态守恒

### 8.1 四个列表不是四个流转牌堆

玩家维护四个卡牌列表，但其中只有三个承担卡牌流转：

| 列表 | 含义 |
| --- | --- |
| `deck` | 本局已拥有卡牌的记录或模板 |
| `drawPile` | 当前可以抽取的牌 |
| `hand` | 当前可操作的手牌 |
| `discardPile` | 已打出或回合结束时弃置的牌 |

`deck` 中的记录不会因为打出一张卡而减少。不能把 `deck.size()` 再加到三个流转牌堆的总数中，否则会重复计数。

### 8.2 卡牌流转路径

```text
抽牌堆 → 手牌 → 弃牌堆
   ↑                │
   └── 空堆时回收并洗牌 ──┘
```

正常出牌时，一张卡从手牌移动到弃牌堆。结束回合时，剩余手牌全部弃置。抽牌堆为空且弃牌堆非空时，将弃牌全部转回抽牌堆并打乱顺序，再继续抽取。

### 8.3 状态不变量

在当前合法流程中，没有消耗卡、复制卡或移除卡效果。因而在每个动作完成后的稳定状态，应满足：

```text
hand.size + drawPile.size + discardPile.size = deck.size
```

初始总数为 10。前三关每成功选择一次奖励，牌组总数加 1，所以进入第 2、3、4 关时通常分别拥有 11、12、13 张牌。

数量守恒还不足以排除所有错误。更严格的测试应检查：同一张运行中的卡没有同时出现在两个流转牌堆里，奖励卡只增加一次，回收弃牌时没有丢失或重复加入卡牌。

### 8.4 新关卡的牌堆准备

选择奖励时，新卡先加入 `deck` 与弃牌堆。之后 `prepareForNewEncounter()` 把当前手牌和弃牌堆并回抽牌堆，清空手牌与弃牌堆，再洗牌。

随后开始新玩家回合，恢复能量、清格挡并抽牌。这保证下一关从整个现有牌组重新组织，而不是只延续上一关剩余的少量抽牌。

## 9 敌人意图与关卡设计

### 9.1 四个关卡

| 关卡 | 敌人 | 最大生命 | 基础攻击 | 击败后处理 |
| --- | --- | --- | --- | --- |
| 第 1 关 | 史莱姆 | 25 | 4 | 选择奖励后进入第 2 关 |
| 第 2 关 | 骷髅士兵 | 40 | 6 | 选择奖励后进入第 3 关 |
| 第 3 关 | 哥布林队长 | 60 | 8 | 选择奖励后进入第 4 关 |
| 第 4 关 | 大魔王 | 90 | 12 | 整局胜利 |

这些值保存在控制器的 `LEVELS` 数组中。当前实现是代码内配置，不是读取 JSON、数据库或外部配置文件。

### 9.2 三种敌人意图

| 意图 | 执行内容 | 首轮之后的抽取概率 |
| --- | --- | --- |
| 攻击 | 对玩家造成基础攻击值的伤害 | 70% |
| 防御 | 敌人获得 6 点格挡 | 20% |
| 攻防 | 造成基础攻击值一半的伤害，并获得 3 点格挡 | 10% |

攻防伤害使用整数除法 `attackDamage / 2`。当前关卡的攻击值均为偶数；若以后配置奇数攻击值，需要明确整数截断是否符合设计。

每个新创建的敌人第一次意图固定为攻击。之后在敌人行动结束时通过 `Math.random()` 生成下一次意图。上述比例是代码定义的单次抽取概率，不意味着短短一局中的实际行为次数一定恰好达到这些比例。

### 9.3 为什么展示意图

意图提前告诉玩家本次结束回合后可能面对的具体伤害或防御，从而让防御选择有依据。敌人行动并非完全隐藏，玩家可以比较“本回合能否击杀”“需要多少格挡”“是否值得承受少量伤害”等选项。

该敌人逻辑属于简单的概率规则系统，不是机器学习模型，也没有实现搜索规划、自适应难度或对玩家策略的学习。

### 9.4 奖励如何形成成长

奖励候选池由五种进阶卡组成。系统先打乱候选池，再取前三张，因此单次三选一中不会出现重复候选；不同关卡仍可能再次抽到相同卡种。

选择卡牌既提高牌组强度，也改变后续抽牌构成。例如重锤提供高伤害但占用两点能量，铁斩波兼顾攻防。玩家需要结合当前牌组和剩余生命选择，而不是只比较一个伤害数字。

目前奖励数值是固定配置，尚没有通过大量统计对局或正式平衡测试证明不同奖励的收益相当。

## 10 核心业务流程的代码实现

### 10.1 战斗初始化

`Main.showGameScene()` 创建控制器。控制器构造函数创建模型、玩家与第一关敌人，初始化状态标记和日志，再调用私有 `startGame()`。

玩家构造函数建立 10 张初始卡牌并洗牌；`startGame()` 再调用玩家 `startTurn()`，补满能量、清格挡并抽取初始手牌。最后视图读取这些状态并展示。

### 10.2 玩家出牌

当前代码的实际先后顺序如下：

1. `GameView` 把被点击卡牌的手牌下标传给控制器。
2. 控制器检查是否为玩家阶段、是否已经终局、是否正在等待奖励。
3. 检查下标是否落在当前手牌范围内。
4. 取出卡牌，记录敌人生命和双方格挡等变化前数据。
5. `Player.playCard()` 检查卡牌有效性、手牌归属与能量。
6. 扣除费用，调用具体卡牌 `play()` 执行效果。
7. 将卡牌从手牌移除并加入弃牌堆。
8. 控制器根据前后数值差异记录日志。
9. 如果敌人死亡，进入奖励等待或整局胜利。
10. 视图调用 `update()`，显示最新状态。

这里应区分“正常校验失败”和“结算中发生异常”。正常校验失败在扣费前返回，不改变战斗资源；但如果扣费后的牌效执行抛出异常，当前代码没有自动回滚机制，不能保证之前的修改被撤销。

### 10.3 结束回合

当前代码的实际顺序为：

```text
检查是否允许结束回合
  → 玩家剩余手牌进入弃牌堆
  → playerTurn 设置为 false
  → 敌人清除旧格挡
  → 敌人执行当前意图
  → 写入伤害和格挡日志
  → 敌人生成下一次意图
  → 检查玩家是否死亡
      → 死亡则设置失败并返回
      → 存活则进入新玩家回合
  → 新玩家回合恢复能量 清玩家格挡并抽牌
```

一个容易讲错的细节是：当前代码会在玩家死亡判定之前生成下次敌人意图，而设计文档描述的是先判定死亡，再生成下一意图。实际介绍代码时，应以前述代码顺序为准。

### 10.4 小怪击败与奖励等待

如果被击败的不是最终 Boss，控制器生成三张奖励候选并把 `rewardPending` 设为 `true`。这时玩家不再通过普通出牌和结束回合推进战斗，而必须先完成选牌。

视图将原来的手牌区域改为奖励候选区域。结束回合按钮被禁用，控制器也会拒绝出牌与结束回合。这既避免界面误操作，也防止绕过按钮直接调用方法推进流程。

### 10.5 选择奖励与下一关

`selectReward(index)` 首先检查奖励等待状态和下标。合法时，将所选卡加入牌组，清空候选并解除奖励等待；然后增加关卡下标，创建下一关敌人，重整玩家牌堆并开始新回合。

跨关卡保留的是同一个玩家对象，所以生命值和累计获得的卡牌得以保留。敌人对象则被替换，新敌人的生命、格挡和首次意图重新初始化。

当前流程没有跳过奖励的选项，也没有选择奖励时的自动治疗。

### 10.6 整局结束与重新开始

击败最终 Boss 后，控制器设置 `gameOver = true`、`playerWin = true`。玩家死亡时设置 `gameOver = true`、`playerWin = false`。终局后的普通出牌和结束回合都会被拒绝。

重新开始通过工厂创建新的控制器，再让视图刷新。它不会保留旧牌组、旧生命或旧关卡，也不是回到菜单后才能开始新一局。

## 11 界面交互与状态刷新

### 11.1 信息布局

战斗界面大致分为三个部分：

- **顶部状态区：** 展示双方生命、格挡和敌人意图。
- **中部交互区：** 展示能量、牌堆数量，以及手牌或奖励卡。
- **底部反馈区：** 展示战斗日志、结束回合和重新开始按钮。

攻击牌与技能牌通过不同配色区分。不可使用的卡牌会禁用并降低不透明度，可使用的卡牌提供悬停放大与阴影反馈。

### 11.2 刷新方式

当前采用事件驱动的同步刷新：点击操作调用控制器，控制器完成逻辑后，界面显式调用 `update()`。没有单独的后台游戏循环，也没有依赖持续逐帧计算来推进战斗。

`update()` 会重新读取状态，更新标签与生命条，清空并重新构建手牌或奖励按钮，同时更新日志。对当前卡牌数量较少的原型来说，这种实现便于理解；如果未来加入大量动画或更复杂交互，就需要重新评估更新粒度。

### 11.3 日志的作用与限制

日志既为玩家解释结果，也帮助开发者检查动作顺序。当前最多保留 100 条，超过时删除最早记录，避免无限增长。

这里限制的是日志条目数量，而不是磁盘日志文件大小。日志保存在内存中，不具备长期保存、复盘存档或完整审计能力。界面的胜负横幅也由视图额外追加显示，不等于一套持久化事件系统。

## 12 关键设计决策及取舍

### 12.1 为什么分层

把规则直接写进按钮事件虽然初期代码短，但会让规则测试依赖窗口，也容易在多个按钮之间重复逻辑。现有结构把规则与交互分开，使界面修改和规则修改通常可以在不同位置完成。

它的代价是增加类之间的调用，并要求开发者持续维护职责边界。当前控制器仍承担较多业务，后续增长时需要进一步拆分，而不是认为创建了三个包就已经彻底解耦。

### 12.2 为什么卡牌使用继承和多态

所有卡牌共享名称、费用与使用入口，但效果不同，适合通过统一抽象入口调用具体实现。这样通用出牌过程不需要知道每张卡的名字。

代价是每种牌效通常对应一个类；当卡牌数量大幅增加时，类数量和硬编码配置也会增长。未来可以评估数据配置与效果组合，但当前代码还没有实现这类系统。

### 12.3 为什么使用事件驱动而不是持续游戏循环

该项目的主要动作由玩家点击和回合结算触发，不需要持续处理角色移动或物理变化。同步完成一次动作再刷新状态，能减少额外线程和中间状态带来的复杂性。

代价是逻辑执行期间没有独立异步动画过程。后续如果增加耗时任务或连续表现，需要避免阻塞界面，并重新设计动画与逻辑完成时机。

### 12.4 为什么把奖励等待单独表示

小怪死亡后到下一关开始之间，存在一个必须让玩家选择的阶段。用 `rewardPending` 明确表示，可以阻止玩家在奖励选择时继续操作旧战斗，并让视图切换到对应界面。

这种做法比把奖励当作一条日志更可靠。但随着暂停、商店、事件等状态增加，多个布尔值可能产生难以理解的组合，因此更完整的状态枚举是后续方向。

### 12.5 为什么重新开始时重建对象

重建控制器会连带重建玩家、敌人、牌组、日志和状态标记，比在旧对象上逐字段重置更不容易遗漏。

当前对象规模小，这种方式结构清楚；如果以后加入共享音频、资源缓存或外部连接，则需要明确哪些资源应复用，哪些状态应重建。

### 12.6 为什么关卡采用配置数组

四个敌人的差异目前主要是名称、生命和攻击，因此用 `EnemyLevel` 记录配置，再复用敌人类即可，避免为每关重复实现同一套战斗行为。

它适合当前需求，但不同 Boss 的复杂机制不能只靠改数值完成，届时需要进一步的行为扩展设计。

## 13 核心难点与处理方法

### 13.1 格挡的生命周期

格挡不是永久生命值。玩家的格挡用于承受接下来的敌人行动，并在新玩家回合开始时清除；敌人的格挡用于承受下一次玩家行动，在下一次敌方回合开始时清除。

如果清除时机提前，刚获得的防御就会失去作用；如果清除时机过晚，格挡可能错误地跨多个回合累积。因此，最难的部分之一是明确“谁的格挡，在谁的回合边界清除”。

对于非负伤害和格挡，规则可写为：

```text
吸收伤害 = min(原格挡, 来袭伤害)
新格挡 = 原格挡 - 吸收伤害
剩余伤害 = 来袭伤害 - 吸收伤害
新生命 = max(0, 原生命 - 剩余伤害)
```

生命减少量与剩余伤害不一定完全相等：例如只剩 2 点生命时承受 10 点剩余伤害，实际生命只减少 2。当前 `takeDamage()` 的返回值是格挡后的剩余伤害，不能在过量伤害场景中直接当作实际生命变化；控制器日志通过比较前后生命值避免了这种混淆。

### 13.2 卡牌流转的一致性

抽牌、出牌、回合弃牌和跨关洗牌都会改变列表。每一步都要同时完成“从来源移除”和“加入目标”，避免丢牌、重复牌或旧手牌残留。

牌堆总数守恒、手牌上限和同一张卡不重复存在，是比仅观察界面更可靠的验证依据。

### 13.3 多关卡状态衔接

同一个“敌人死亡”事件，在小怪关和最终关的后续流程不同。除此之外，进入下一关时还要同时处理敌人替换、牌堆重整、能量恢复、格挡清除和生命保留。

因此关卡切换不能只写一个下标加一。正确实现需要把状态迁移作为一个完整流程，并在流程完成后验证各项状态。

### 13.4 随机性与测试可重复性

初始洗牌、弃牌回收、奖励候选和敌人意图都包含随机性。随机结果有助于玩法变化，却可能让同一个测试走过不同路径。

当前代码没有统一注入可控随机源，测试仍依赖自然抽牌和意图。这是已有验证能力的限制。后续应让测试能固定牌序、意图或随机种子，再分别测试正常路径、失败路径和边界条件。

### 13.5 界面限制不能替代规则限制

禁用按钮只控制当前界面入口。控制器仍然需要检查阶段和下标，模型仍需要检查卡牌归属与能量。

当前 `canPlayCard()` 主要服务界面可用性判断，不完整检查卡牌是否属于手牌。真正执行时仍要通过控制器下标检查及 `Player.playCard()` 的归属检查，不能把它当作通用出牌授权方法。

## 14 测试现状与验证方案

### 14.1 已有测试组织

现有 `GameControllerTest` 包含 12 个普通测试方法和 1 个参数化测试方法。参数化方法提供三个无效下标输入，因此完整展开对应 15 个执行实例。

已有测试涉及初始化、攻击牌、防御牌、无效下标、出牌后资源变化、奖励选牌、结束回合、胜负判断、日志和卡牌可用性。但“有对应名称的测试”不等于“场景已经得到充分验证”，还要检查前置条件和断言是否真的执行。

### 14.2 已有报告与时间边界

工程中现存测试报告文件最后写入时间为 **2026 年 9 月 15 日 13 时 57 分 36 秒**。报告记录：执行 15 个实例，1 个失败、0 个错误、0 个跳过，即 14 个通过；失败项为 `victoryCondition`。

这是已有报告，不是本次编写说明时重新运行得到的结果。本说明没有把它作为当前代码全部行为已通过验证的证据，也没有给出未经确认的覆盖率或性能数据。

### 14.3 通关测试遗漏了什么

`victoryCondition` 一直循环出牌和结束回合，却没有调用 `selectReward()`。当击败第一关敌人进入奖励等待后，这两个战斗操作都会被控制器拒绝，因此该路径无法正常推进到最终 Boss。

问题说明了一个重要原则：多阶段业务的测试必须处理所有必要的中间状态。修正思路应是逐段检查：

```text
本关击败敌人
  → 确认进入奖励等待
  → 确认存在三张候选
  → 选择合法奖励
  → 确认牌组与关卡变化
  → 继续下一关
  → 最终 Boss 死亡后确认整局胜利
```

完成路径修正后仍要重新运行，不能仅凭代码思路就宣称测试已经通过。

### 14.4 条件性断言的问题

攻击和技能测试在“抽到对应卡”时才执行断言；终局禁用测试也在“循环后已经结束”时才进入断言。这些写法存在前置条件不满足而没有真正验证目标行为的风险。

更可靠的做法是直接构造目标状态，或先对前置条件作断言，再执行动作。不能把“测试方法正常返回”简单等同于“测试目标已被覆盖”。

### 14.5 建议补齐的测试矩阵

以下是验证方案，不是已通过清单。

| 类别 | 场景 | 关键断言 |
| --- | --- | --- |
| 初始化 | 创建新控制器 | 80 生命、3 能量、5 手牌、第 1 关、非终局 |
| 出牌 | 能量恰好等于费用 | 成功，能量归零，卡仅移动一次 |
| 出牌 | 能量不足 | 拒绝，生命、格挡和牌堆等战斗数据不变 |
| 出牌 | 下标为负或等于手牌数 | 拒绝，不发生越界异常 |
| 牌效 | 七种具体卡牌 | 精确断言费用、伤害和格挡变化 |
| 格挡 | 小于、等于、大于来袭伤害 | 生命与剩余格挡均符合公式 |
| 抽牌 | 抽牌堆空但弃牌非空 | 回收后继续抽牌，数量守恒 |
| 抽牌 | 两个牌堆都空 | 不越界，不凭空生成卡 |
| 抽牌 | 手牌已经达到 10 张 | 不继续增加手牌 |
| 回合 | 普通结束回合 | 剩余手牌弃置，敌人行动，再恢复能量和抽牌 |
| 回合 | 敌人造成致命伤害 | 判负，不继续新玩家回合抽牌 |
| 奖励 | 小怪被击败 | 出现三张候选，战斗操作被锁定 |
| 奖励 | 合法选择一次 | 牌组加一、关卡加一、生命保留 |
| 奖励 | 重复选择或无效下标 | 拒绝，不重复加卡或跳关 |
| 终局 | 最终 Boss 被击败 | 整局胜利，普通战斗操作被拒绝 |
| 重开 | 中途或终局后重新开始 | 关卡、生命、牌组和日志不保留旧局状态 |
| 日志 | 连续产生超过 100 条 | 仅保留最近 100 条 |

### 14.6 测试应分三个层次

**规则测试：** 不启动窗口，直接验证卡牌、生命、格挡与牌堆。

**流程测试：** 调用控制器，检查完整状态迁移，尤其是奖励、下一关和终局。

**界面验收：** 检查显示与状态同步，按钮是否正确禁用，奖励区域是否切换，重新开始是否可用。

设计文档提出的接口化改造完成后，还可以引入模型和视图替身，单独验证控制器是否发出了正确调用。这是后续能力，不是当前已有测试结构。

## 17 现有限制与后续改进

### 17.1 当前限制

- **测试尚未闭环。** 现有通关用例缺少奖励处理，部分测试存在条件性断言，尚不能宣称全路径已稳定验证。
- **状态访问不严格只读。** 模型对象与牌堆列表暴露给调用方。
- **随机性难以统一控制。** 使用 `Math.random()` 与无显式随机源的洗牌，确定性测试不够便利。
- **异常不具备事务式恢复。** 捕获异常和输出日志不能撤销已发生的扣费或中间修改。
- **结构还有集中化倾向。** 模型集中于一个外部类，控制器同时承担关卡、奖励、日志和战斗协调。
- **配置硬编码。** 卡牌、关卡和概率保存在 Java 代码里。
- **内容与表现范围有限。** 暂无地图、存档、音效和复杂表现系统。
- **界面扩展需要再评估。** 当前手牌采用固定尺寸横向布局；若未来经常接近 10 张上限，应补充适配或滚动布局验证。
- **缺少正式性能和平衡数据。** 未进行可引用的性能基准、长时间稳定性或大量自动对局统计。

### 17.2 建议的改进顺序

**第一阶段 统一事实与补足测试。** 更新 README 和设计文档，修正奖励与通关测试，补全能量、格挡、牌堆、失败和重新开始的边界验证。

**第二阶段 降低耦合。** 拆分模型实体，引入明确的战斗操作接口和只读状态对象，并统一随机源的创建和注入方式。

**第三阶段 整理状态与配置。** 评估用状态枚举替代多个布尔组合，将卡牌与关卡配置外置，并为复杂牌效或敌人行为建立扩展方式。

**第四阶段 扩展玩法与体验。** 在规则稳定后增加更多敌人、卡牌、地图、存档和表现效果。新增能力必须同步增加状态转换与测试，而不只是增加按钮。

这些是建议路线，不是已完成的功能，也不代表已经确定的交付承诺。

## 18 可直接使用的项目介绍稿

### 18.1 简短介绍版本

我们的项目是一个基于 Java 和 JavaFX 的单机回合制卡牌游戏，参考了杀戮尖塔的核心战斗形式。玩家每回合获得三点能量，利用手中的攻击牌和防御牌与敌人战斗。项目包含四个连续关卡，前三关击败敌人后可以从三张奖励卡中选一张加入牌组，最终击败 Boss 完成通关。技术上，我们把界面展示、流程控制和战斗规则分开，重点实现了卡牌多态、牌堆循环、敌人意图和跨关卡状态管理。

### 18.2 详细介绍版本

我们的项目是基于 JavaFX 实现的杀戮尖塔简化版。它不是对原作全部内容的复刻，而是把抽牌、能量消耗、攻防结算和战后奖励这些核心机制组合成一个完整的桌面游戏流程。

从玩家角度看，进入游戏后，每回合有三点能量，并尝试抽取五张卡牌。玩家可以先查看敌人的下一步意图，再选择攻击还是防御。打出的卡牌会进入弃牌堆，回合结束时没有使用的手牌也会弃置；抽牌堆用完后，弃牌会重新洗回抽牌堆，因此卡牌能够循环使用。

游戏设置了三个小怪和一个最终 Boss。每击败一个小怪，玩家都能从三张候选奖励中选一张加入牌组，再进入下一关。玩家的生命和已有卡牌会跨关保留，所以除了考虑当前回合伤害，还需要考虑后续生存与牌组搭配。

技术上，项目采用 MVC 思路。View 负责 JavaFX 界面和操作反馈，Controller 负责回合、关卡、奖励和胜负流程，Model 负责卡牌效果、生命、格挡和牌堆规则。不同卡牌通过继承抽象 Card 类实现各自效果，通用出牌过程只需要调用统一的 play 方法。

我们认为实现中最需要注意的是状态变化顺序。比如玩家的格挡必须先承受敌人的攻击，再在新回合开始时清除；小怪被击败后必须先进入奖励等待，而不能直接跳到下一关或整局胜利。这些细节如果顺序错误，界面看起来仍可能正常，但实际规则已经不正确。

测试方面，项目已经有 JUnit 用例，但还存在需要完善的地方，例如通关用例没有覆盖奖励选择，部分用例依赖随机手牌。后续重点是统一代码与设计文档，引入可控随机源，补全格挡、牌堆和完整通关路径的测试，再逐步落实文档中提出的接口与只读快照设计。

总的来说，这个项目的重点不是功能数量，而是把一个交互式战斗流程用清晰的对象和状态组织起来，并让关键规则能够被解释和验证。

## 19 常见问题与回答

### 为什么选择 JavaFX

本项目需要桌面窗口、按钮、标签、布局容器和生命条，JavaFX 可以在同一套 Java 工程中完成这些界面与交互。这里的选择适用于当前课程原型，并不意味着它对所有游戏项目都是最优方案。

### 项目最核心的业务是什么

以回合为单位管理资源和状态：玩家出牌，系统扣费并结算效果，敌人执行意图，随后判定胜负或开始下一回合；多关卡奖励把单次战斗连接成整局流程。

### 如何保证没有能量时不能出牌

界面先根据 `canPlayCard()` 禁用按钮，执行时控制器再检查流程和下标，玩家模型最终检查手牌归属与能量。正常拒绝路径发生在扣费之前。

### 为什么不直接把所有功能写进一个类

集中在一个类会让界面、规则和流程互相牵动，也不便于独立测试。现在的分层降低了一部分修改影响，但仍有进一步拆分空间。

### 敌人是否具有人工智能

敌人通过三种意图和概率抽取选择行动，可以称为简单的规则型敌人逻辑。它不包含学习、搜索或复杂推理。

### 玩家下一关会恢复生命吗

不会。当前跨关保留同一个玩家对象，没有自动治疗逻辑；能量、格挡与牌堆会按新回合和新遭遇规则准备。

### 设计文档中的接口和快照是否已经实现

没有。当前代码仍采用 `GameController` 与 `GameModel` 的直接协作方式。接口和快照是文档提出的方案，适合作为后续改造目标。

### 项目是否已经全部测试通过

不能这样表述。已有报告包含一个失败项，测试源码还有需要补齐的路径与断言。本说明也没有重新执行测试或确认覆盖率。

### 捕获异常是否能保证不会出问题

不能。异常捕获能够记录问题并避免某些异常直接继续向外传播，但并不自动撤销此前的状态修改，也不能保证所有情况下界面和规则都恢复正常。

### 如果继续开发 最值得先做什么

先统一版本说明，修复并补全测试，再收紧状态访问和随机源控制。规则验证可靠后，再扩展卡牌、敌人和玩法。
